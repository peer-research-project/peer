## Candidate architecture

1. Extend profile JSON + existing upload ledger and browser-supplied seedTexts. Lowest upfront work, but cannot guarantee per-owner authoritative version, unique canonical seeds, non-expiring assets, owner-day activation, cross-device transactional updates, private server-side job parity or no double count. Reject as authoritative store.
2. Dedicated owner-scoped seed pool + immutable version/snapshot metadata and private seed asset namespace (recommended). A server-side owner/date resolver is common to web, direct digest and prepared jobs; it returns version, distinct usable feature sets, effective date and tombstone generation. Changes use compare-and-swap/transaction (latest pending wins), first-ever nonempty usable pool becomes active immediately, otherwise stage for next owner local date. Account-bound RLS/API and explicit no-seed fallback preserve privacy and compatibility. Moderate migrations and integration; atomic DB activation plus fail-closed asset cleanup handles concurrency and partial failures.
3. Precompute every day’s complete recommendations and store their seed version, with no common seed resolver. Highest write/storage and replay complexity; offline/email may be consistent only if every artifact preexists, new seed creation/future jobs race, and delete/forget must invalidate all artifacts. Reject as primary architecture; snapshots should represent pool state, not become the only source of truth.

## Proposed activation and lifecycle contract to rule

A server-side resolver accepts authenticated owner, IANA timezone and target local date. Under transaction/compare-and-swap, read the pool state and immutable version referenced for that date; return no-seed legacy mode or one distinct feature vector per ready canonical paper, an opaque deterministic version and revocation generation. Never trust owner ID, feature vectors or seed version from a browser payload. First pool activates on the first successfully parsed seed and is reflected in the first briefing, including clearing/replacing a still-unserved pre-seed prepared batch. Later latest pending pool is scheduled for the next local calendar date (not duration), with undo canceling/restoring pending state and concurrent edits protected by revision. On target date, promote exactly once atomically. For future-dated preparation resolve the snapshot for job.localDate, and fence both pre/post build against that date's pool version; edit or privacy deletion invalidates/rebuilds unserved work. Once served, keep the day stable for ordinary edits. Explicit forget is the exception: immediately revoke access/inference and purge PDF, sidecar, derived features plus versioned caches/unserved outputs; already delivered external email cannot be recalled. In-flight work checks tombstone/version before result publication and before send. Storage/DB deletion is not one transaction: persistent revocation first, asynchronous retryable cleanup, no successful-delete claim until verified, and never rehydrate from stale browser state.

Score components: strongest per-seed similarity 0..1 at .40, declared intent 0..1 at .35, explicit feedback 0..1 at .15, recency/source combined 0..1 at .10; if feedback absent, reassign its .15 to intent as requested, preserving total1. Unknown seed similarity stays distinguishable from zero. Keep strongest one or two for evidence/diversity, but never add copies' contribution. Rank/dedupe canonical copies before/through every channel; enforce hard excludes, source access and ownership first; record matched concepts and seed identifiers privately to generate a truthful reason. Do not introduce paid models or transmit private PDF text in public neighbor requests. Initial weights are a hypothesis, not a quality guarantee.
